# Architecture — Phase 2 (Executable Reconciliation & Evaluation Layer)

This document locks the deterministic/LLM boundary and the JSON schema
contract before any code was written, per Plan V4 Stage A.

## Non-goals (restated, binding)

- The 21 taxonomy pattern-checks are **not** made deterministic. Reading a
  free-text deployment plan and judging whether evidence satisfies a
  pattern's criteria is a genuine language-understanding task and stays
  LLM-based.
- `SKILL.md` is not replaced. It still performs the actual review reasoning.
  This phase only changes what happens *after* SKILL.md produces findings.
- The taxonomy (`taxonomy-v2.md`), severity rubric, and the existing
  100-case corpus are not touched. They stay exactly as validated in v1.

## Deterministic / LLM-assisted line

| Task | Classification |
|---|---|
| Reading the deployment plan and deciding if pattern C4's evidence criteria is met | LLM-assisted |
| Writing the Finding / Evidence / Risk / Mitigation prose | LLM-assisted |
| Assigning a severity to a *new* finding | LLM-assisted |
| Counting how many CRITICAL/HIGH/ADVISORY findings exist | Deterministic |
| Checking that all 21 pattern IDs are accounted for | Deterministic |
| Checking severity/confidence values are in the fixed enum | Deterministic |
| Comparing findings against ground truth for eval scoring | Deterministic |

The rule of thumb: anything that requires reading and interpreting the
deployment plan's prose is LLM-assisted; anything that only requires reading
the LLM's own **structured output** is deterministic.

## Hybrid pipeline

```
deployment plan (free text)
        |
        v
LLM-assisted review (SKILL.md logic, unchanged)
        |
        v
structured output (JSON — see schema below)
        |
        v
deterministic reconciliation engine (reconciliation.py, real code)
        |
        v
validated final findings report (+ pass/fail flag)
```

The reconciliation engine never asks the model to re-derive or re-confirm
its own summary counts. It computes them itself from the findings list, so
a summary can no longer disagree with the findings — that disagreement is
no longer representable in the output.

## JSON schema contract

The LLM-assisted review step must emit one JSON object per case:

```json
{
  "case_id": "case-28",
  "findings": [
    {
      "pattern": "S1",
      "severity": "CRITICAL",
      "finding": "Same factory-default maintenance PIN shipped on every lock",
      "evidence": "Plan states the same 4-digit code ships on every lock from the factory.",
      "risk": "A single known PIN compromises maintenance-mode override on any of 8,000 locks.",
      "mitigation": "Require a property-specific PIN at installation; disable the factory default.",
      "confidence": "HIGH"
    },
    {
      "pattern": "COMPOUND(S1,S2)",
      "severity": "CRITICAL",
      "finding": "Proximity-reachable diagnostic interface combined with a universal factory-default PIN.",
      "evidence": "Builds on the S1 and S2 findings above.",
      "risk": "Materially worse combination for a physical-security product than either finding alone.",
      "mitigation": "Prioritize both fixes together.",
      "confidence": "HIGH"
    }
  ],
  "no_gap_patterns": ["C1", "C2", "C3", "C4", "C5", "P1", "P2", "P3", "P4", "P5",
                       "O1", "O2", "O3", "O4", "O5", "S3", "S4", "S5", "S6"]
}
```

Rules the reconciliation engine enforces against this schema:

1. **Coverage**: every one of the 21 base pattern IDs (C1–C5, P1–P5, O1–O5,
   S1–S6) must appear exactly once, either in a `findings` entry's
   `pattern` field or in `no_gap_patterns` — never both, never neither.
   `COMPOUND(...)` entries are additional and don't count toward coverage.
2. **Enum validity**: `severity` ∈ {CRITICAL, HIGH, ADVISORY};
   `confidence` ∈ {HIGH, MEDIUM, LOW}. No free-text drift.
3. **Summary is computed, not trusted**: the human-readable summary line
   (`Findings: X Critical, Y High, Z Advisory`) is generated by
   `reconciliation.py` by counting the `findings` list itself. The schema
   has no separate summary field for the model to (mis)state, which is
   what makes the case-28/case-49 arithmetic-mismatch bug class
   structurally impossible rather than merely unobserved.

A case that fails rule 1 or rule 2 is marked `INVALID` by the engine and
excluded from eval scoring, exactly as the current reconciliation gate in
`harness.py` already does for count mismatches — this phase extends that
gate from "compare two numbers" to "verify full structural coverage."
